## Доброго дня!

Используемые технологии: **Helm**, **Argo CD**, **Argo CD Image Updater**

Созданные манифесты: **argocd/application.yaml**, **argocd/image-updater.yaml**

### Про Helm:

Вроде ничего необычного с чартами не делал. Просто вставил манифесты из прошлой дз, чутка их доработал и сделал параметризованными. Почему выбрал Helm? Я изучал kustomize и писал в чатик о нем пост. Как по мне, он посложнее... В плане у helm просто values меняешь и все, буквально все в одном месте. А патчи kustomize везде, всюду и повсюду...

### Про Argo CD:

Провел установку с HA манифеста в надежде, что на live-demo при отключении одной из нод Argo CD не будет шокирован. Добавил также секреты с токенами гитлаба и докерхаба в namespace argocd. application вроде тоже стандартный, только приложение разворачиваю в отдельном namespace myapp.

### Про Argo CD Image Updater:

Тут вообще история... Попытался я в общем через annotations в application, и как-то не шло, плюс в документации вообще нет примеров с annotations. Вот и решил отдельно создать ImageUpdater по примеру из документации. Версионность основывется на semver.

Также пришлось чутка переписать Jenkinsfile. Так как ImageUpdater коммитит под логином argocd-image-updater, добавил проверку по этому. Условно с помощью git show вытягиваю логин и сравниваю с argocd-image-updater. Если не совпадают, то логическая переменная isHuman принимает значение True. И у меня были другие логические переменные по типу shouldTag, shouldBuild и так далее. Их я переделал по типу

(условие 1 или условие 2 или условие 3) и isHuman

По итогу выходит так, что если не человек, то многие этапы пропускаются. Итого остается только этап Checkout и Lint and SAST. Таким образом я избегаю зацикливания, когда бот вносит изменения, новый коммит, новый пайплайн, новый образ и так по кругу.

### Про видео:
В видео показываю как все работает. Начинаю с показа существующих тегов. Там видно, что есть последний v1.0.34. Аналогично по тегам на докерхабе. Также показываю, что существует приложение в Argo CD с образом v1.0.34. Вношу изменения в код, коммит, создание пайплайна. Потом с этого коммита создаю тег v1.0.35. Jenkins видит, что создался тег и вызывает пайплайн для такого случая. На одном из этапов этого пайплайна происходит пуш нового образа в докерхаб. Дальше просто ожидание, пока ImageUpdater проверит и закоммитит и задеплоит.
